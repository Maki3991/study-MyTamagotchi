# 14｜Failed to fetch：这个项目里其实有两个后端

## 这一篇要解决的问题

你之前看到过：

    无法连接后端：Failed to fetch
    演化引擎暂时离线

这两个现象不一定指向同一个服务。

当前仓库里同时存在两个不同的后端：

    Python FastAPI 后端：8000 端口
    Node 世界演化引擎：8787 端口

这一篇只学习如何区分它们。

## 1. 先看两个后端分别负责什么

### Python FastAPI 后端

位置：

    backend/

启动方式：

    .\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000

它负责：

    Agent 列表
    Agent 详情
    Agent 派遣
    Plaza
    Skills
    SQLite 数据

前端请求地址通常是：

    http://127.0.0.1:8000/api

backendApi.ts 第 6 行附近规定了这个默认地址。

### Node 世界演化引擎

位置：

    frontends/mobile/server/

启动方式：

    npm run backend

默认端口：

    8787

它负责：

    世界演化
    世界 tick
    文明历史
    一部分世界叙事功能

前端在 main.tsx 第 12 行附近会使用：

    http://127.0.0.1:8787/api

去检查世界演化服务是否在线。

这个 Node 服务的 README 已经说明：它是非主线参考服务，手机端的主要 Demo 后端仍然是 backend/ 里的 Python FastAPI。

## 2. 为什么项目里会有两个后端？

这个项目是在黑客松期间逐步组合出来的。

Python 后端负责当前手机端主要使用的数据和业务：

    Agent
    Plaza
    Skills
    SQLite

Node 服务保留了另一套世界演化引擎：

    世界 tick
    事件
    文明状态
    JSON 文件保存的世界状态

它们不是同一个程序，也不使用同一个主要数据存储。

可以这样看：

| 服务 | 端口 | 主要数据 | 当前定位 |
|---|---:|---|---|
| Python FastAPI | 8000 | tamagotchi.db | 手机端主要业务后端 |
| Node 世界引擎 | 8787 | server/data/world-state.json | 世界演化参考服务 |

## 3. 从 Network 的请求地址判断是哪一个后端

打开 Network 后，先看请求网址中的端口。

### 看到 8000

例如：

    http://127.0.0.1:8000/api/agents/3/dispatch

这是 Python FastAPI。

它对应：

    backend/app/main.py
    backend/app/db.py
    backend/tamagotchi.db

如果这个请求 Failed to fetch，优先检查 Python 后端是否启动。

### 看到 8787

例如：

    http://127.0.0.1:8787/api/health
    http://127.0.0.1:8787/api/world

这是 Node 世界演化引擎。

如果这个请求 Failed to fetch，通常表现为：

    演化引擎暂时离线
    世界没有继续演化
    相关世界状态无法加载

它不一定代表 Agent、Plaza 和 SQLite 后端也离线。

## 4. 你现在使用的启动组合是什么？

如果你按照当前推荐方式启动：

终端 1：

    backend/.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

终端 2：

    npm run frontend

那么运行的是：

    Vite 前端
    + Python FastAPI 后端

这时：

    Agent、Plaza、Skills 应该可以使用
    Node 世界演化引擎没有启动
    依赖 8787 的演化功能可能显示离线

这是一个有意的启动组合，不代表前端整体坏了。

## 5. npm run dev 为什么容易让人混淆？

frontends/mobile/package.json 中：

    npm run dev

实际执行的是：

    node server/dev-all.mjs

这个脚本会尝试同时启动：

    frontends/mobile/server/index.mjs
    npm run frontend

也就是：

    Node 世界演化引擎
    + Vite 前端

它不会启动 backend/ 里的 Python FastAPI。

因此，如果你的目标是研究 Agent、Plaza 和 SQLite，当前更清晰的组合是：

    Python FastAPI 8000
    + npm run frontend

不要把两个后端混成一个服务理解。

## 6. 看到 Failed to fetch 时的判断顺序

### 第一步：看端口

    8000：检查 Python 后端
    8787：检查 Node 世界演化引擎

### 第二步：看功能

    Agent、Plaza、Skills
    → 先看 8000

    世界演化、tick、文明历史
    → 再看 8787

### 第三步：看对应终端

8000 的终端应该出现 Uvicorn 运行信息。

8787 的终端应该出现类似：

    ForkWorld engine: http://127.0.0.1:8787

哪个服务的端口没有监听，就检查哪个服务的启动命令。

## 7. 结合你之前看到的页面现象

你之前看到 Agent 和 Plaza 显示在线数据时，说明：

    8000 的 Python 后端已经正常工作

如果同一时间某个世界仍然显示：

    演化引擎暂时离线

那可能只是：

    8787 的 Node 世界演化服务没有启动

这两个结果可以同时成立：

    Agent 数据正常
    Plaza 数据正常
    世界演化引擎离线

因为它们来自两个不同的后端。

## 8. 以后向 AI 描述 Failed to fetch

不要只说：

    页面显示 Failed to fetch。

最好提供：

    请求网址
    请求端口
    请求路径
    页面功能
    对应后端终端是否运行

例如：

    点击 Agents 后，请求
    http://127.0.0.1:8000/api/agents
    显示 Failed to fetch。
    Python Uvicorn 终端没有启动。

或者：

    Scene 页面请求
    http://127.0.0.1:8787/api/health
    显示 Failed to fetch。
    Agent 和 Plaza 的 8000 请求正常。

这两种问题的排查方向完全不同。

## 小结

- 当前项目存在 Python FastAPI 和 Node 世界演化两个后端。
- 8000 负责 Agent、Plaza、Skills 和 SQLite。
- 8787 负责另一套世界演化服务。
- Network 中的端口可以直接告诉你请求去了哪个后端。
- npm run frontend 只启动前端，配合 Python 后端使用。
- npm run dev 会尝试启动 Node 服务和前端，不会启动 Python FastAPI。
- Failed to fetch 必须结合请求地址、端口和功能一起判断。
