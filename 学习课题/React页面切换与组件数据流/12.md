# 12｜怎样证明 AI 的修改真的生效了？

## 这一篇要解决的问题

看到页面发生变化，只能证明“你眼前的页面变了”。

要确认一个跨层功能真的工作，需要检查：

    页面动作
    → 浏览器请求
    → 后端处理
    → 数据库变化
    → 页面最终结果

这一篇继续使用“派 Agent 到 Plaza”作为例子。

## 1. 四个证据点分别证明什么？

| 证据点   | 你要确认什么                           |
| -------- | -------------------------------------- |
| 页面     | 用户是否能够触发动作，界面是否显示结果 |
| Network  | 浏览器是否真的发出了正确请求           |
| 后端终端 | 后端是否收到请求，处理时是否报错       |
| SQLite   | 数据是否真的写入并长期保存             |

四个地方看到的结果可能不同。

例如：

    页面看起来没有变化
    但数据库已经保存成功

这说明问题可能在前端刷新或重新渲染。

也可能出现：

    页面按钮可以点击
    但 Network 中没有请求

这说明动作没有走到请求层。

## 2. 第一步：记录操作前的状态

在 DB Browser for SQLite 中打开：

    backend/tamagotchi.db

查看 Agent 表中目标 Agent 的：

    id
    location
    profile

假设当前记录是：

    id = 3
    location = learning-commons

同时记住这个 Agent 的名字，避免观察错记录。

这一步的意义是建立“修改前”的证据。

## 3. 第二步：在页面触发功能

打开手机端页面，进入目标 Agent 的详情卡片，点击：

    派往广场

当前项目中，这个动作的前端位置是：

    App.tsx:1664

此时不要只看页面有没有变化，还要同时观察浏览器开发者工具。

## 4. 第三步：在 Network 中看请求

在 Chrome 中：

1. 按 F12 打开开发者工具；
2. 进入 Network；
3. 点击派遣按钮；
4. 找到 agents/.../dispatch 这一条请求。

重点看 4 个地方：

### 请求地址

应该对应：

    /api/agents/{agent_id}/dispatch

例如 Agent id 是 3，就会包含：

    /api/agents/3/dispatch

### 请求方法

应该是：

    POST

因为这是一次会改变数据的动作。

### 请求内容

派往广场时，应该包含：

    location: "plaza"

### 返回内容

成功后，返回数据里的 location 应该是：

    plaza

如果这 4 项都正确，说明：

    页面已经把正确动作发送给后端
    → 请求格式基本没有问题

backendApi.ts 中对应的位置是第 152–155 行。

## 5. 第四步：看 Network 的状态结果

Network 中还要看请求的状态。

可以先这样理解：

| 状态            | 说明                       |
| --------------- | -------------------------- |
| 200             | 后端成功处理并返回结果     |
| 400             | 请求内容不符合后端规则     |
| 404             | 找不到接口或找不到 Agent   |
| 500             | 后端处理时发生错误         |
| Failed to fetch | 浏览器没有成功拿到后端响应 |

如果页面出现 Failed to fetch，重点先检查：

    后端是否正在运行
    请求地址是否正确
    前端代理是否指向正确端口

这时还没有必要先检查数据库。

## 6. 第五步：看后端终端

后端通常在另一个终端中运行：

    uvicorn app.main:app --port 8000

发送请求后，观察这个终端：

    是否出现请求记录
    是否出现 Python Traceback
    是否提示 Agent 不存在
    是否提示 location 不合法

派遣规则的后端位置是：

    backend/app/main.py:245

如果 Network 显示请求已经发出，但后端终端出现错误，问题就在后端处理阶段。

例如：

    Network：POST 请求，状态 500
    后端终端：出现数据库或 Python 错误

这时页面只是最后显示了失败结果，根源在后端。

## 7. 第六步：回到 SQLite 看是否真的保存

请求成功后，回到 DB Browser：

1. 刷新数据库；
2. 重新打开 Browse Data；
3. 查看同一个 Agent 的 location；
4. 查看 profile 中是否出现 home_world。

预期结果：

    location = plaza
    profile.home_world = 派遣前的世界

如果数据库仍然是：

    location = learning-commons

就说明数据没有真正写入，或者你查看的不是后端正在使用的数据库文件。

数据库路径由：

    backend/app/db.py:5

决定，实际文件是：

    backend/tamagotchi.db

当前项目使用 SQLite WAL 模式，旁边可能还有：

    tamagotchi.db-shm
    tamagotchi.db-wal

如果程序仍在运行，DB Browser 中看不到最新结果时，可以先刷新数据库，必要时关闭并重新打开数据库。

## 8. 第七步：确认页面结果

最后回到页面，检查：

    Agent 详情中的位置是否更新
    Plaza 是否出现这个 Agent
    原来的世界是否不再显示它

如果数据库已经是 plaza，但页面仍然显示旧世界，说明：

    后端和数据库已经成功
    → 前端没有重新读取或重新显示最新数据

这时应该检查 App.tsx 中的：

    setDetail
    refreshMyAgents
    onChanged

不需要回头修改数据库。

## 9. 一次完整验证应该得到什么结果？

以 Agent id 为 3 为例：

| 检查位置     | 预期结果                      |
| ------------ | ----------------------------- |
| 修改前数据库 | location = learning-commons   |
| 页面点击     | 点击派往 Plaza                |
| Network 地址 | /api/agents/3/dispatch        |
| Network 方法 | POST                          |
| Request Body | location = plaza              |
| Response     | location = plaza              |
| 后端终端     | 没有异常                      |
| 修改后数据库 | location = plaza              |
| profile      | home_world = learning-commons |
| 页面         | Agent 出现在 Plaza            |

这一组结果同时成立，才可以说这条功能链验证通过。

## 10. 根据现象定位问题在哪一层

| 现象                   | 优先检查                               |
| ---------------------- | -------------------------------------- |
| 按钮没有反应           | App.tsx 的点击逻辑                     |
| 没有 Network 请求      | 前端动作没有调用 backendApi            |
| Failed to fetch        | 后端进程、端口、代理或网络连接         |
| 请求是 400             | 请求内容违反后端规则                   |
| 请求是 404             | 地址、Agent id 或接口不存在            |
| 请求是 500             | main.py、models.py、db.py 或数据库错误 |
| 请求 200，但数据库没变 | commit、数据库路径或查看的文件不对     |
| 数据库变了，但页面没变 | 前端刷新或显示逻辑                     |

这个表的作用是减少盲目修改。

你不需要一开始就让 AI 重写整个 App。先根据证据判断问题在哪一层，再让 AI 检查对应文件。

## 11. 以后如何验收 AI 的修改？

让 AI 修改功能前，先确定：

    修改前是什么结果？
    修改后应该是什么结果？
    哪个请求应该发生？
    哪个数据库字段应该变化？
    用什么页面操作可以复现？

修改完成后，按照相同顺序验证：

    页面
    → Network
    → 后端终端
    → SQLite
    → 页面最终结果

这就是你参与 AI 编程时最重要的验收能力之一。

## 小结

- 页面变化不等于整个功能链成功。
- Network 可以证明浏览器是否发出了正确请求。
- 后端终端可以证明请求是否被正确处理。
- SQLite 可以证明数据是否真正保存。
- 页面最终结果可以证明前端是否正确读取和显示。
- 不同现象对应不同排查层，不要一看到页面问题就直接修改数据库。

## 学习反馈

假设出现下面的情况：

    Network 显示 POST 成功，状态是 200；
    SQLite 里的 location 也已经变成 plaza；
    但页面仍然显示 Agent 在原来的世界。

你觉得这时应该优先检查哪一层：前端刷新显示、后端规则，还是数据库保存？

先检查前端刷新嘛，对吧？要么是你后端传数据给前端的过程可能出了点问题，要么是你前端收到了数据，然后解读数据可能有点问题。反正的话就是你前端刷新有问题。或者说你后端没有在把数据修改了之后及时传递信号给前端，所以说没有渲染。反正的话就是回来那个信号出了点问题，要么是它发送的过程中，要么是它被解读的过程中。
