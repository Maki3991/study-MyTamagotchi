# 20｜总复盘：从用户动作追踪到数据库和页面

## 这一讲的作用

这一讲不增加新的 React、TypeScript 或 FastAPI 知识。

它只把前面学过的内容整理成一张项目地图，让你以后看到一个功能时，能够回答：

1. 用户动作从哪个前端文件开始？
2. 它有没有向后端发请求？
3. 后端哪个函数接收了请求？
4. 数据库改变了什么？
5. 页面最后怎样显示结果？

## 一、这个项目的整体结构

当前我们主要研究的是 mobile 前端和 Python 后端：

~~~text
浏览器中的 React 页面
  ↓
frontends/mobile/src/app/App.tsx
  ↓
frontends/mobile/src/app/backendApi.ts
  ↓
Python FastAPI，8000 端口
  ↓
backend/app/main.py
  ↓
backend/app/db.py
  ↓
backend/tamagotchi.db
~~~

各个位置的职责：

| 位置 | 负责什么 |
|---|---|
| App.tsx | 页面、按钮、前端状态、组件之间的数据传递 |
| backendApi.ts | 把前端业务动作转换成 HTTP 请求 |
| main.py | 接收请求、执行后端规则、返回数据 |
| db.py | 连接 SQLite、提供数据库 Session |
| models.py | 描述 Agent、Memory、Skill 等记录有哪些字段 |
| tamagotchi.db | 保存实际数据 |

之前看到的 Node 世界演化服务属于另一条服务线。当前主线围绕 Agent、Plaza、Skills 和 SQLite，主要使用 8000 端口的 Python 后端。

## 二、第一条链：读取 Agent 列表和详情

### 1. 打开 Agents 页面

用户打开 Agents 页面后：

~~~text
AgentsDirectoryScreen
→ backendApi.agents()
→ GET /api/agents
→ main.py 的 list_agents
→ 查询 Agent 表
→ 返回 Agent 列表
→ agents 保存列表
~~~

相关位置：

~~~text
App.tsx:5499
backendApi.ts:129-130
main.py:193-199
~~~

### 2. 生成卡片

前端使用 agents 列表生成一张张卡片：

~~~text
agents.map(agent => ...)
~~~

每一张卡片的数据里已经有：

~~~text
agent.id
agent.name
agent.location
agent.mood
~~~

### 3. 点击一张卡片

用户点击 id 为 3 的 Agent：

~~~text
agent.id = 3
→ expandedId = 3
~~~

expandedId 只表示哪张卡片要展开。

### 4. 获取详情

前端继续请求：

~~~text
backendApi.agent(3)
→ GET /api/agents/3
→ main.py 的 get_agent(3)
~~~

后端读取：

~~~text
id = 3 的 Agent
这只 Agent 的 memories
这只 Agent 的 skills
~~~

前端收到结果后：

~~~text
setDetail(row)
→ detail 保存详情
→ 当前卡片显示 Skills 和记忆
~~~

这一条链的核心区别是：

~~~text
agents
→ 多只 Agent 的基础列表

detail
→ 当前一只 Agent 的详细资料
~~~

## 三、第二条链：派遣和召回 Agent

派遣和召回使用同一个按钮、同一个 toggleDispatch 函数。

按钮根据当前位置显示不同文字：

~~~text
不在 Plaza
→ 显示“派去广场”

在 Plaza
→ 显示“召唤回家”
~~~

### 1. 前端决定目标

~~~text
toggleDispatch
→ 当前不在 Plaza，就把目标设为 plaza
→ 当前在 Plaza，就把目标设为 home
~~~

### 2. 发送 POST 请求

~~~text
backendApi.dispatch(...)
→ POST /api/agents/{id}/dispatch
~~~

请求体可能是：

~~~json
{ "location": "plaza" }
~~~

或者：

~~~json
{ "location": "home" }
~~~

### 3. 后端修改数据库

~~~text
main.py 的 dispatch_agent
→ 找到 Agent
→ 判断目标
→ 修改 agent.location
→ 保存 home_world
→ session.commit()
→ 返回更新后的 Agent
~~~

这里的 home 是一个“召回指令”。后端会把它转换成 Agent 之前所属的实际世界。

### 4. 更新详情卡片

后端返回后：

~~~text
setDetail
→ 更新 AgentProfileSheet 里的 detail
→ 详情卡片显示新位置
~~~

### 5. 更新外层 Agent 列表

详情卡片随后调用：

~~~text
onChanged
→ refreshMyAgents
→ GET /api/agents?owner_id=1
→ setDbMyAgents
~~~

dbMyAgents 是 App 顶层保存的“我的 Agent 列表”。Scene、Inventory 等页面使用它。

这一条链的核心区别是：

~~~text
detail
→ 详情卡片中的单个 Agent

dbMyAgents
→ 外层页面使用的 Agent 列表
~~~

只更新 detail，详情卡片可能已经变了；重新更新 dbMyAgents，外层世界才能拿到最新位置。

## 四、两个 API 方法怎样配合

在 Network 面板中，派遣或召回通常能看到：

~~~text
POST /api/agents/8/dispatch
→ 执行位置修改

GET /api/agents?owner_id=1
→ 重新读取我的 Agent 列表
~~~

因此可以这样记：

| 方法 | 当前功能中的作用 |
|---|---|
| POST | 告诉后端执行派遣或召回，并修改数据库 |
| GET | 重新读取修改后的 Agent 列表 |

POST 返回的是单个更新后的 Agent，GET 返回的是多只 Agent 的列表。

## 五、以后看到陌生功能，使用这条路线

不要从整个项目开始阅读。先选一个具体动作，例如：

~~~text
点击召回
点击某个 Agent
打开 Agents 页面
~~~

然后按照下面顺序查：

### 第一步：找页面入口

看按钮的 onClick、页面组件或用户看到的文字。

### 第二步：找前端业务函数

例如：

~~~text
toggleDispatch
backendApi.agents
backendApi.agent
~~~

### 第三步：找网络请求

记录：

~~~text
请求方法：GET / POST / PATCH / DELETE
请求地址：/api/...
请求体：发送了什么数据
~~~

### 第四步：找后端接口

在 main.py 中找到对应的：

~~~text
@app.get(...)
@app.post(...)
~~~

### 第五步：找数据变化

如果是读取，确认查询了什么。

如果是修改，确认修改了哪个字段、是否执行了 session.commit()。

### 第六步：找页面更新

确认后端返回后，前端更新了哪个变量：

~~~text
setDetail
setDbMyAgents
setAgents
~~~

## 六、以后让 AI 修改代码时，应该要求它回答什么

你可以直接复制下面这段话给 AI：

~~~text
请只分析“用户点击召回”这一条功能链，不要逐行解释语法。

请告诉我：
1. 用户动作从哪个文件、哪个函数开始；
2. 前端调用了哪个 backendApi 函数；
3. 发送了什么 HTTP 方法、什么 URL 和请求数据；
4. 后端 main.py 的哪个函数接收；
5. 数据库哪个字段发生变化；
6. 后端返回什么结果；
7. 前端哪个变量被更新；
8. 页面最终通过什么数据重新显示。

每一步都写文件路径和行号。
~~~

## 七、如何验证 AI 的修改

修改完成后，不需要先理解所有代码。可以先检查四类证据：

### 页面证据

按钮、位置、列表和详情是否符合预期。

### Network 证据

请求方法、地址、请求体、响应状态码是否正确。

### 后端终端证据

FastAPI 是否报错，接口是否正常返回。

### SQLite 证据

Agent 的 location、profile 等实际字段是否已经改变。

一个成功的派遣或召回通常应当形成：

~~~text
页面动作正确
→ POST 返回 200
→ 数据库字段改变
→ GET 列表返回新数据
→ 页面显示新位置
~~~

## 八、这 20 讲最终要带你获得什么能力

你不需要记住 App.tsx 中的所有函数，也不需要独立写出整个 React 项目。

当前阶段的目标是：当 AI 说“我修改了 Agent 派遣功能”时，你能继续追问：

~~~text
改了哪个前端入口？
调用了哪个 API？
后端哪个接口处理？
数据库改了什么？
页面为什么会更新？
我应该在哪里验证？
~~~

这就足以让你参与技术方案讨论、检查 AI 的修改，并发现“数据库成功但页面仍旧”的问题。
