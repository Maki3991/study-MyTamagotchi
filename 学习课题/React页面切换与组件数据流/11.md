# 11｜文件职责表：AI 修改哪个文件，会影响什么？

## 这一篇要解决的问题

前面我们追踪了“派 Agent 到 Plaza”这条功能链。

现在把它整理成一种以后可以反复使用的阅读方法：

    看到一个文件名
    → 判断它属于哪一层
    → 判断它负责输入、处理、保存还是显示
    → 预判 AI 修改它会影响什么

这一篇不要求你阅读每个文件的全部代码。

## 1. “文件职责”是什么意思？

文件职责就是用一句话说明：

    这个文件在整个功能中负责哪一件主要事情？

例如：

    backendApi.ts：把手机端的业务动作发给后端

这句话不要求你知道文件里的每一行代码，但可以帮助你判断：

    如果要修改请求地址，应该先看这个文件。

## 2. 派遣 Agent 功能的文件职责表

| 文件 | 所属层 | 主要职责 | 在派遣功能中做什么 |
|---|---|---|---|
| App.tsx | 手机端界面 | 接收用户操作、组织页面、更新显示 | 确定派哪个 Agent、调用派遣动作、刷新界面 |
| backendApi.ts | 手机端与后端之间 | 统一封装请求 | 发送 Agent id 和目标 location |
| main.py | 后端业务层 | 接收接口请求、执行规则、返回结果 | 检查 Agent 和位置，修改 location |
| models.py | 后端数据结构 | 描述数据库表和字段 | 声明 Agent 有 location、profile 等字段 |
| db.py | 后端数据库连接层 | 连接 SQLite、创建 session | 让 main.py 可以读取和提交数据库 |
| tamagotchi.db | 数据保存层 | 保存实际记录 | 保存 Agent 当前的 location 和 profile |

把它们按运行顺序排列：

    App.tsx
    → backendApi.ts
    → main.py
    → models.py + db.py
    → tamagotchi.db
    → main.py 返回结果
    → App.tsx 显示结果

这里不是每个文件都“依次执行一遍”。

更准确地说：

    App.tsx 发起动作
    → main.py 处理请求
    → main.py 使用 db.py 和 models.py 访问数据库
    → tamagotchi.db 保存结果
    → main.py 返回结果
    → App.tsx 更新界面

## 3. AI 修改 App.tsx，可能影响什么？

App.tsx 主要影响手机端的：

    用户能不能点击
    页面显示什么
    当前状态如何变化
    什么时候调用 backendApi
    收到结果后是否重新显示

例如 AI 修改 App.tsx：

    把“派往 Plaza”按钮隐藏
    → 可能只是用户看不到按钮

    修改按钮点击后的调用
    → 可能导致请求没有发出去

    收到后端结果后不再刷新列表
    → 数据已经保存，但页面仍然显示旧位置

所以看到 AI 修改 App.tsx 时，重点检查：

    用户还能不能触发动作？
    请求是否仍然发出？
    收到结果后页面是否更新？

## 4. AI 修改 backendApi.ts，可能影响什么？

backendApi.ts 影响的是手机端和后端之间的请求格式。

它可能改变：

    请求地址
    请求方法
    请求体里的字段
    后端返回结果的读取方式

例如后端仍然要求：

    { location: "plaza" }

但 AI 把前端发送的字段改成：

    { target: "plaza" }

后端就可能无法按照原来的规则工作。

所以看到 AI 修改 backendApi.ts 时，重点检查：

    请求地址有没有变？
    POST、PATCH、GET 是否仍然正确？
    发给后端的字段名是否和后端一致？
    后端返回的数据，前端是否还能读取？

## 5. AI 修改 main.py，可能影响什么？

main.py 负责后端接口和业务规则。

如果 AI 修改 dispatch_agent，可能影响：

    哪些 Agent 可以被派遣
    哪些位置是合法的
    home 如何找到原来的世界
    修改是否真正提交数据库
    返回给前端哪些数据

例如需求是：

    Agent 不能被派到 Plaza，只能被派到自己的三个世界。

主要应该先看 main.py 的派遣规则，而不是先改 CSS 或按钮文字。

看到 AI 修改 main.py 时，重点检查：

    规则是否符合产品需求？
    数据库修改是否仍然执行？
    出错时是否返回明确结果？
    前端收到的返回格式是否仍然一致？

## 6. AI 修改 models.py，可能影响什么？

models.py 描述数据库表的结构。

如果只是修改界面文字，通常不需要改 models.py。

如果需求是：

    给 Agent 增加一个新的数据字段

例如：

    favorite_place

那么可能需要同时考虑：

    models.py 是否增加字段
    现有数据库是否需要迁移
    main.py 是否读写这个字段
    backendApi.ts 是否接收或发送这个字段
    App.tsx 是否显示它

所以 models.py 的修改通常比普通 UI 修改影响更大。

看到 AI 修改 models.py 时，重点检查：

    是增加字段、删除字段，还是修改字段含义？
    旧数据库里的数据还能不能使用？
    是否需要迁移？
    哪些接口和页面会受到影响？

## 7. AI 修改 db.py，可能影响什么？

db.py 负责后端如何连接数据库。

它决定：

    数据库文件在哪里
    后端如何创建连接
    请求如何获得数据库 session
    程序启动时是否创建或迁移表

修改 db.py 可能影响所有需要数据库的接口，而不只是 Agent 派遣。

例如数据库路径改错，可能出现：

    程序启动了
    但读取的是另一个空数据库
    页面显示没有 Agent
    你以为数据丢失了

因此 db.py 属于影响范围较大的基础文件。

## 8. tamagotchi.db 和代码文件的区别

tamagotchi.db 是数据文件，不是业务代码。

它保存的是当前状态，例如：

    Agent 1 的 location = plaza
    Agent 2 的 location = learning-commons

代码文件决定：

    数据有哪些字段
    数据如何读取
    什么情况下允许修改
    修改后如何保存

数据库文件保存：

    这一次实际运行后，当前数据是什么

所以当 AI 修改“派遣规则”时，通常应该修改代码；数据库会在程序运行时按照新规则产生变化。

不应该让 AI 直接把数据库文件当成普通文本文件修改。

## 9. 用需求反推应该看哪些文件

以后可以先从需求反推文件范围。

### 需求一：只改变按钮颜色

优先看：

    App.tsx
    或具体的 UI 组件文件

### 需求二：修改派遣请求地址或字段

优先看：

    backendApi.ts
    main.py

### 需求三：修改派遣规则

优先看：

    main.py

同时验证：

    数据库里的 location 是否正确变化
    手机端是否显示最新结果

### 需求四：给 Agent 增加一个长期保存的字段

可能涉及：

    models.py
    db.py 的迁移逻辑
    main.py
    backendApi.ts
    App.tsx
    tamagotchi.db 的实际结构

这就是“影响范围”的概念。

## 10. 以后让 AI 修改功能时，可以先问这 5 句话

    这次需求属于界面、请求、业务规则还是数据库结构？

    你准备修改哪些文件？每个文件负责什么？

    数据从哪里来，修改后保存在哪里？

    前端、后端和数据库之间的字段是否一致？

    我应该怎样操作和检查，才能确认修改完成？

你不需要自己写出答案，但可以要求 AI 先把答案讲清楚，再开始修改。

## 小结

- 文件职责让你不用读完整个项目，也能判断一个文件在做什么。
- App.tsx 主要负责手机端交互和页面显示。
- backendApi.ts 主要负责前端请求与后端接口之间的连接。
- main.py 主要负责后端接口和业务规则。
- models.py 描述数据库结构，db.py 负责连接数据库。
- tamagotchi.db 保存真实运行数据。
- AI 修改不同文件，影响范围不同；数据库结构和连接文件通常影响更大。
