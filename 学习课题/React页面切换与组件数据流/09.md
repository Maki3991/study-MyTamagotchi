# 09｜Python 文件里的 Agent 和数据库里的 Agent 是什么关系？

## 这一篇要解决的问题

你已经能够复述：

    点击派遣
    → 前端发送请求
    → 后端处理
    → 数据库修改
    → 前端显示结果

现在只补一个关键问题：

    Agent 的数据到底在哪个地方？

我们要区分 4 个东西：

1. 手机端暂时拿到的 Agent 数据；
2. 后端 Python 程序运行时加载的 Agent；
3. models.py 对 Agent 数据结构的描述；
4. SQLite 文件里真正长期保存的 Agent 记录。

## 1. 手机端最开始从哪里得到 id 和 location？

当你点击某个 Agent，手机端会打开 Agent 的详情卡片。

相关位置：

    App.tsx:1623
    App.tsx:1639

详情卡片会向后端请求这个 Agent 的详细资料：

    backendApi.agent(agentId)

这个请求最终对应：

    GET /api/agents/{agent_id}

后端在 main.py 第 203 行附近根据 agent_id 查找 Agent，并返回包括这些内容的 JSON：

    id
    name
    mood
    location
    profile
    memories
    skills

手机端收到 JSON 后，把它暂时放进详情卡片自己的 detail 数据中。

所以当你点击派遣时，前端已经知道：

    detail.id
    detail.location

它们不是凭空产生的，也不是手机端自己猜出来的，而是之前从后端读取回来的。

## 2. models.py 保存数据吗？

位置：backend/app/models.py，第 21–30 行。

这里有：

    class Agent

它描述 Agent 应该有哪些字段：

    id
    owner_id
    name
    image
    trait
    mood
    location
    profile

models.py 的作用是描述数据结构。

它本身不是当前 Agent 数据的保存地点。它告诉后端：

    Agent 这类数据有这些字段
    Agent 应该对应数据库中的一张表

因此可以这样区分：

    models.py：说明 Agent 表应该长什么样
    tamagotchi.db：保存 Agent 表当前有哪些记录、每条记录的值是什么

## 3. Python 里的 Agent 是什么？

后端收到请求时，会执行：

    session.get(Agent, agent_id)

这一步的结果可以理解为：

    从 SQLite 中找到这一条 Agent 记录
    → 暂时加载到 Python 程序里
    → 得到一个可以读取和修改的 Agent 对象

因此，在后端处理过程中同时存在两种形态：

| 形态                   | 作用                                 |
| ---------------------- | ------------------------------------ |
| SQLite 中的 Agent 记录 | 长期保存，程序重启后仍然存在         |
| Python 中的 Agent 对象 | 当前请求处理期间，方便后端读取和修改 |

Python 对象是后端从数据库加载出来的当前副本。

如果只修改 Python 对象，数据库文件不会自动永久改变。后端还需要提交保存动作。

## 4. location 修改后到底保存在哪里？

后端处理派遣时，核心过程是：

    agent = session.get(Agent, agent_id)
    → 找到数据库中的 Agent

    agent.location = target
    → 修改当前 Python 对象里的 location

    session.commit()
    → 把修改写回 SQLite

所以全过程是：

    数据库记录
    → 加载成 Python 对象
    → 修改 Python 对象
    → commit
    → 写回数据库记录

最终真正长期保存的位置是：

    backend/tamagotchi.db

其中 Agent 表的 location 字段会从例如：

    learning-commons

变成：

    plaza

models.py 没有保存这次具体的变化。它只负责描述 location 这个字段存在。

## 5. 原来的世界保存在哪里？

派遣到 Plaza 时，后端需要记住 Agent 原来来自哪个世界。

代码在 backend/app/main.py 第 257–260 行附近：

    profile["home_world"] = agent.location

这里的意思是：

    把派遣前的 location 复制到 profile 里的 home_world

例如：

    location = learning-commons
    → profile 里记录 home_world = learning-commons
    → location 改成 plaza

这个项目没有单独建立一个 previous_location 字段。

它把 home_world 放进了 Agent 的 profile 字段。models.py 第 29 行说明 profile 是一段 JSON 文本。

因此派到 Plaza 后，一条 Agent 记录大致可以理解为：

    location = plaza
    profile = {
      "home_world": "learning-commons"
    }

之后召回时：

    前端发送 location = home
    → 后端读取 profile 里的 home_world
    → 得到 learning-commons
    → 把 agent.location 改回 learning-commons
    → commit 保存

## 6. 后端最后返回什么？

后端提交数据库后，会调用 agent_out。

位置：backend/app/main.py，第 108 行附近。

它把 Python 中已经更新后的 Agent 整理成 JSON，返回给手机端。

返回结果中包含：

    id
    name
    mood
    location
    profile

手机端收到这个结果后：

    更新详情卡片里的 location
    → 通知外层页面刷新 Agent 列表
    → Scene 和 Plaza 根据新的 location 重新显示

因此“后端返回数据给前端”并不是把数据库文件发给前端，而是把这次操作后的结果整理成 JSON 发回去。

## 7. 这几个文件分别负责什么？

把整条链中的文件重新整理：

| 文件          | 它负责什么                                   |
| ------------- | -------------------------------------------- |
| App.tsx       | 接收用户点击，决定当前要派哪个 Agent         |
| backendApi.ts | 把 Agent id 和目标位置发给后端               |
| main.py       | 接收请求、检查规则、修改 Agent、返回结果     |
| models.py     | 描述 Agent 表有哪些字段                      |
| db.py         | 告诉后端 SQLite 文件在哪里，并提供数据库连接 |
| tamagotchi.db | 保存真正的 Agent 记录和字段值                |

特别注意：

    models.py 不是数据库
    main.py 不是数据库
    Python 中的 agent 对象也不是永久数据
    tamagotchi.db 才是长期保存当前值的地方

## 8. 用一张数据变化表看完整过程

假设一个 Agent 原本在 Learning Commons。

| 时刻          | Python 对象中的 location | 数据库中的 location    | profile 中的 home_world |
| ------------- | ------------------------ | ---------------------- | ----------------------- |
| 派遣前        | learning-commons         | learning-commons       | 可能为空                |
| 派遣处理中    | plaza                    | 尚未提交前可能仍是旧值 | learning-commons        |
| commit 后     | plaza                    | plaza                  | learning-commons        |
| 召回后 commit | learning-commons         | learning-commons       | learning-commons        |

这张表说明：

    Python 对象是处理过程中的当前对象
    数据库记录是长期保存的结果
    home_world 是为了支持召回而保留的来源信息

## 小结

- Agent 的 id 和 location 最初由后端接口返回给手机端。
- models.py 描述数据库表结构，不保存某个 Agent 的当前值。
- Python 中的 Agent 对象是从数据库加载出来、供当前请求处理的对象。
- 修改 Python 对象后，commit 才会把变化真正写入 SQLite。
- 当前 location 保存在 Agent 表的 location 字段。
- 原来的世界保存在同一条 Agent 记录的 profile JSON 中，名称是 home_world。
- 后端最后返回的是更新后的 Agent JSON，不是整个数据库文件。
