# 13｜问题定位演练：页面没变化时先查哪里？

## 这一篇要解决的问题

你在上一讲的判断是：

    Network 成功
    → 数据库也已经更新
    → 页面仍然显示旧内容
    → 优先检查前端收到结果后的刷新和显示

这个判断是正确的。

这一篇把它整理成以后可以重复使用的排查顺序。

## 1. 先把“页面没有变化”拆成几个可能的位置

用户看到的现象相同，问题位置可能不同：

    点击后根本没有请求
    请求发出但失败
    请求成功但后端返回旧数据
    数据库没有保存
    数据库已经保存，但页面仍使用旧数据

所以不能只根据“页面没变化”就直接判断某一个文件出错。

需要按照请求链逐层确认。

## 2. 第一种情况：没有 POST 请求

如果点击派遣后，Network 中没有：

    POST /api/agents/{id}/dispatch

说明动作没有走到后端请求。

优先检查：

    App.tsx 的按钮点击处理
    backendApi.dispatch 是否被调用

此时数据库和后端规则还没有必要先看，因为请求根本没有出发。

## 3. 第二种情况：POST 请求失败

如果 Network 中出现 POST，但状态不是成功状态：

### Failed to fetch

优先检查：

    后端是否启动
    端口是否正确
    前端请求地址是否正确
    代理或跨域是否配置正确

### 400

说明后端收到了请求，但请求内容不符合规则。

例如：

    location 不是允许的位置

### 404

说明接口地址或 Agent id 找不到。

### 500

说明后端处理过程中发生了异常。

此时查看运行 Uvicorn 的终端，寻找错误信息。

## 4. 第三种情况：POST 成功，但 Response 不对

假设 Network 显示：

    POST
    200 OK

还不能马上认为功能完全正确。

点击“响应”查看后端返回的数据。

如果你请求的是：

    location = plaza

但响应里仍然是：

    location = learning-commons

说明问题可能在后端处理或返回结果：

    main.py 没有正确修改 Agent
    或返回给前端的对象仍然是旧值

这时优先检查 main.py 和数据库提交过程。

## 5. 第四种情况：Response 正确，但数据库不对

假设 Response 显示：

    location = plaza

但 SQLite 里仍然是：

    location = learning-commons

需要检查：

    session.commit() 是否执行
    后端使用的数据库路径是否正确
    DB Browser 打开的是否是同一个 tamagotchi.db
    数据库是否还没有刷新

如果程序读取的是另一个数据库文件，你可能会看到：

    页面显示一套数据
    DB Browser 显示另一套数据

所以 db.py 中的 DB_PATH 是重要证据。

## 6. 第五种情况：Response 和数据库都正确，但页面还是旧的

这是你上一讲判断的情况。

完整证据是：

    Network Response：location = plaza
    SQLite：location = plaza
    页面：Agent 仍显示在原世界

此时后端和数据库已经完成了工作。

问题集中在前端收到结果之后：

    前端有没有更新自己的数据
    刷新函数有没有被调用
    页面显示使用的是不是旧列表
    页面是否根据新的 location 重新判断位置

当前项目中需要关注：

    App.tsx:1669 附近的 setDetail
    App.tsx:1670 附近的 onChanged
    App.tsx:6648 附近的 refreshMyAgents

这几个位置共同决定：

    后端返回的新 Agent
    是否进入前端当前使用的数据

## 7. 为什么刷新浏览器后可能恢复正常？

浏览器刷新会重新启动前端页面。

页面启动时，前端会再次向后端请求 Agent 列表。

这时它拿到的是数据库里已经保存的新 location，所以画面恢复正确。

因此：

    刷新后正确
    不刷新时错误

通常说明数据库里的最终数据可能已经正确，旧问题更可能出现在：

    当前页面没有及时重新读取数据
    或重新读取后没有使用新数据重新显示

这也是你之前发现“收回后刷新才显示”的重要线索。

## 8. 一张定位表

| 观察结果                          | 优先检查                            |
| --------------------------------- | ----------------------------------- |
| 没有 POST                         | App.tsx、按钮动作                   |
| POST 不存在或地址错误             | backendApi.ts                       |
| POST 400                          | 请求内容和后端规则                  |
| POST 404                          | Agent id 或接口地址                 |
| POST 500                          | main.py、db.py、models.py、后端终端 |
| POST 200，但 Response 错          | main.py 的业务处理                  |
| Response 正确，但数据库旧         | commit、数据库路径、DB Browser 刷新 |
| Response 和数据库都正确，但页面旧 | App.tsx 的刷新和渲染                |

这张表可以帮助你把“感觉不对”变成一个具体排查位置。

## 9. 这对 AI 协作有什么用？

以后你可以向 AI 提供证据，而不是只说：

    派遣功能好像有 Bug。

可以这样描述：

    点击派遣后，POST /api/agents/3/dispatch 返回 200。
    Response 中 location 已经是 plaza。
    SQLite 中 location 也是 plaza。
    但返回 Scene 后，页面仍然显示 Agent 在原来的世界。
    浏览器刷新后显示正确。

AI 根据这组证据，应该优先检查前端数据刷新和显示逻辑。

这会比让 AI 盲目搜索整个 App.tsx 更有效。

## 小结

- 页面没有变化只是现象，不是故障位置。
- 先确认有没有请求，再看请求状态、Response、数据库和页面。
- Network 的 Response 正确，说明后端已经把结果发回来了。
- 数据库正确但页面旧，重点检查前端刷新和显示。
- 刷新后恢复正常，是“前端旧数据没有及时更新”的重要线索。
- 提供完整证据后，AI 才能更准确地定位文件和修改范围。
