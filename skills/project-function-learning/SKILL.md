# 项目功能拆解学习

## 目标

把一个真实项目里的一个功能讲成一条可以跟随的链路，让学习者能够回答：

> “我做了什么操作？哪个文件先响应？数据经过了哪些地方？最后为什么页面变了？”

本 Skill 面向希望通过项目理解开发、但不想先系统学习所有语法的人。默认用中文，默认少放代码，优先解释职责、顺序、数据和验证方法。

如果 `$dbs-learning` 可用，把本 Skill 的功能链讲解方式与它的连续课程、反馈调整、学习计划结合起来；如果不可用，仍然按照下面的独立流程工作。

## 必须遵守的讲解原则

1. **一次只拆一个真实功能。** 例如“点击派遣按钮后，Agent 从家里变成 Plaza 状态”。不要同时讲整个前端、所有路由或所有组件。
2. **先说本讲要回答什么。** 开头用一句话说明用户动作、预期结果和本讲边界。
3. **按时间顺序讲主链。** 默认沿着这条链查找：

   `用户操作 → 页面组件 → 事件函数 → 前端状态/API → HTTP 请求 → 后端路由 → 数据库 → 响应 → 前端状态 → 页面更新`

   如果某个功能没有后端或数据库，在相应位置停止，不要为了完整而引入无关层。
4. **代码少而准确。** 只展示能帮助定位的短片段；不要逐行翻译代码，也不要默认教授 `useState`、TypeScript 类型或框架语法。用户明确要求时再展开。
5. **使用真实位置。** 给出实际文件路径和大致行号；如果行号因代码变化不稳定，说明函数名并给出搜索关键词。不要凭常见项目结构猜测文件名。
6. **区分概念角色。** 明确说明某个名字是组件、变量、状态 setter、事件处理函数、API 封装、后端路由、数据库访问函数还是数据库表/字段。
7. **不要混淆“临时页面数据”和“持久数据库数据”。** 说明哪个值只存在于前端内存，哪个值已经写入数据库，以及刷新页面后数据从哪里重新读取。
8. **保持一条主线。** 如果 Scene、Plaza、Agents、详情弹窗存在多个入口，先选择与用户操作直接相关的一条；其余路径标记为“之后再看”，不要在同一讲展开。
9. **以反馈调整颗粒度。** 用户说“看不懂”时，不要求用户准确指出术语，而是主动回退：先复述用户操作和结果，再只讲阻断理解的一个节点。用户说“太简单”时，再增加下一层文件或验证方式。

## 工作流程

### 1. 确定一个可观察的目标

从用户的问题中提取一个具体动作，例如：

- 点击 Agent 卡片后，详情为什么出现？
- 点击“派遣到 Plaza”后，数据库和页面分别怎么变化？
- 刷新页面后，为什么之前的数据还在？

如果目标过大，主动缩小为一个按钮、一个页面切换或一条请求链。先给出本讲边界，不要直接开始讲整个仓库。

### 2. 只读取定位所需的项目材料

先查看项目的 README、规则文件、入口文件和相关目录；再用文件搜索定位实际实现。优先使用 `rg --files`、`rg -n` 或等效搜索，避免把大型文件全文倾倒给学习者。

至少确认：

- 前端从哪里启动，页面由谁组织；
- 用户操作所在的组件和事件入口；
- API 请求封装在哪里；
- 后端路由或控制器在哪里；
- 数据库访问层、模型/表和实际数据库文件在哪里。

如果只找到一部分，明确说“目前能确认到这里”，不要假装已经确认完整链路。

### 3. 先画出极简功能链，再解释节点

先用 4—8 个编号节点给出流程全貌，每个节点只写“谁做什么”。例如：

1. 详情组件收到点击事件。
2. 事件函数读取当前 Agent 的位置。
3. API 封装把目标位置交给 `fetch`，发出 `POST`。
4. 后端路由找到对应 Agent 并修改数据库。
5. 后端返回修改后的 Agent。
6. 详情状态先更新，再通知外层列表刷新。
7. React 根据新状态重新显示按钮文字和位置。

之后只解释用户当前不理解的节点，不重新讲一遍所有 React 基础。

### 4. 用四层框架解释每个节点

对每个节点回答下面四个问题：

| 层 | 要回答的问题 |
| --- | --- |
| 页面/组件 | 谁负责显示这部分界面？它是组件，不是数据库或按钮本身吗？ |
| 前端逻辑 | 哪个函数响应点击？哪个状态保存当前显示的数据？ |
| API/后端 | 请求发到哪里？使用 GET、POST、PATCH 还是 DELETE？后端哪个路由接收？ |
| 数据/结果 | 数据库读写了什么？返回后哪个前端状态改变？页面因此哪里改变？ |

遇到名称相似的对象，必须用一句话区分。例如：

- `AgentsDirectoryScreen` 是显示 Agent 列表的组件；
- `AgentProfileSheet` 是显示单个 Agent 详情的组件；
- `toggleDispatch` 是响应按钮的函数，不是按钮本身；
- `dbMyAgents` 是前端列表状态，不是数据库文件；
- `list_agents` 是后端批量查询的路由处理函数；
- `db.py` 通常提供数据库连接/会话能力，但具体查询可能由路由函数调用。

### 5. 只解释当前必需的术语

用当前链路中的职责定义术语，不给脱离项目的百科解释。例如：

- `fetch`：浏览器实际发 HTTP 请求的工具；
- `req`：项目作者对 `fetch` 的统一包装，负责拼 URL、设置选项、检查错误和解析响应；
- `GET/POST/PATCH/DELETE`：请求想表达的操作类型，不是 `fetch` 的替代品；
- `useState`：让组件保存一份会影响页面显示的前端状态；
- `setXxx`：改变那份前端状态并触发重新渲染的函数；
- `id`：让后端知道用户正在操作哪一个具体对象。

如果术语不影响当前主线，先不讲。

### 6. 给出可验证的观察点

每讲至少提供一个适合学习者执行的验证方式：

- 页面上观察按钮文字、位置或列表数量是否改变；
- DevTools Network 查看请求 URL、方法、请求载荷和响应；
- 后端终端观察是否收到请求或报错；
- DB Browser for SQLite 刷新对应表，确认持久数据是否改变。

明确区分 `OPTIONS` 预检请求和真正的 `POST/GET` 请求；不要把预检误认为业务请求。

## 每讲的输出格式

除非用户要求其他形式，按下面顺序输出：

1. **本讲目标**：一句话说明只研究哪个动作和结果。
2. **先看全流程**：4—8 个编号节点的时间顺序。
3. **文件定位**：文件路径、函数/组件名、大致行号、职责。
4. **节点解释**：只解释会阻断当前理解的概念和数据变化。
5. **怎么验证**：给一个 UI、Network、终端或数据库观察点。
6. **本讲结论**：用 2—4 句话复述主链。
7. **反馈入口**：邀请用户说明“哪一个节点让思路中断”，但不要要求用户先准确命名问题。
8. **下一步**：只提出一个相邻的小目标，并说明为什么接它。

不强行写成正式长课文。如果用户只是追问一个概念，就直接回答概念，并把它放回当前功能链。

## 反馈驱动的调整规则

- 用户说“我完全看不懂”：退回到用户动作、页面结果和 3—4 个节点；暂时不出现新文件名。
- 用户说“我不知道它是什么”：先判断它属于组件、函数、变量、请求还是数据库对象，再说明职责。
- 用户说“我找不到”：给出绝对/相对文件路径、函数名、搜索词和大致行号；必要时直接在项目中定位。
- 用户说“概念懂了但代码作用不明”：只拿一个短代码片段解释“输入、动作、结果”，不讲整段语法。
- 用户说“太抽象”：改用当前项目中实际出现的名字和一次具体点击，不新增比喻。
- 用户说“太简单”：补充下一层的实际文件和验证方式，但仍保持一个功能主线。
- 用户补充反馈后，再决定是否生成下一篇；不要为了凑课数重复已经掌握的内容。

如果与 `$dbs-learning` 一起使用：读取学习计划和最近一篇文章，依据反馈决定下一篇的标题、范围和深度；完成一篇后更新计划。若项目已有课程目录，沿用其编号和反馈记录，不另建平行课程。

## 交付标准

一次讲解完成后，学习者不必能自己重写代码，但应该能说清：

- 这次用户操作要实现什么；
- 哪个组件显示、哪个函数响应；
- 数据经过哪个 API 和后端处理；
- 数据库是否被改变；
- 哪个前端状态被更新，页面为什么随之变化；
- 如果出问题，下一步去哪里观察。

若无法达到这些标准，减少范围并继续定位，不要用更多术语掩盖链路缺口。
