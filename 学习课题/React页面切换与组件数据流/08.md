# 08｜派 Agent 到广场：一条功能如何经过前端、后端和数据库？

## 这一篇要解决的问题

这一篇只追踪你已经实际操作过的一个功能：

    把自己的 Agent 派到 Plaza
    或者把它从 Plaza 收回原来的世界

我们暂时不拆 JSX、TypeScript、对象解构等语法，只回答：

    用户点击以后，程序的哪一层做了什么？

## 1. 先看这个功能的最终效果

这个功能改变的不是当前页面，而是 Agent 的位置。

Agent 的位置有 4 种可能：

    vitality-gym-town
    learning-commons
    maker-harbor
    plaza

因此，“派去广场”实际是在修改一条数据：

    这个 Agent 当前位于哪里？

如果位置是 plaza，三个世界就不再把它当作自己的居民；Plaza 才会把它当作广场里的 Agent。

## 2. 第一步：用户在手机端点击

位置：frontends/mobile/src/app/App.tsx，第 1658–1675 行附近。

这个区域中有一个功能动作：派去广场／召回原世界。

用户点击后，手机端先判断当前情况：

    如果 Agent 当前不在 Plaza，就派到 Plaza
    如果 Agent 当前已经在 Plaza，就请求召回

这个判断使用了两个信息：

    当前 Agent 的 id
    当前 Agent 的 location

所以手机端此时要做的事情是：

    确定是哪一个 Agent
    → 确定这次要去哪里
    → 把这两个信息交给请求函数

手机端此时还没有直接修改 SQLite。它只是准备向后端报告用户的操作。

## 3. 第二步：backendApi 把动作送给后端

位置：frontends/mobile/src/app/backendApi.ts，第 108–124 行和第 152–155 行。

在这个文件里，backendApi.dispatch 专门表示：

    请求后端移动某个 Agent

它需要两个输入：

    agentId：哪个 Agent
    location：要移动到哪里

它发出的请求可以翻译成：

    POST /api/agents/某个 Agent 的 id/dispatch

请求内容：

    { location: "plaza" }

或者：

    { location: "home" }

这里的 POST 表示“向后端提交一次会改变数据的动作”。

backendApi.dispatch 不负责决定数据库怎样修改。它负责把手机端已经确定好的动作送到后端，并接收后端返回的结果。

## 4. 第三步：后端接收并检查

位置：backend/app/main.py，第 240–264 行。

后端对应的接口是：

    /api/agents/{agent_id}/dispatch

后端收到请求后，按照这个顺序处理：

1. 根据 agent_id 查找 Agent。
2. 如果找不到，返回“Agent 不存在”。
3. 读取请求中想要去的位置。
4. 检查目标位置是否属于允许的范围。
5. 如果请求是 home，就找这个 Agent 之前所在的世界。
6. 修改 Agent 的 location。
7. 保存修改。
8. 把更新后的 Agent 信息返回给手机端。

这就是后端的价值：它负责检查规则，并执行真正的数据修改。

## 5. 为什么召回时使用 home？

派遣到 Plaza 时，后端会先记住 Agent 原来所在的世界：

    profile["home_world"] = agent.location

例如：

    Agent 原来在 learning-commons
    → 被派到 plaza
    → 后端记录 home_world = learning-commons

之后手机端请求：

    location = "home"

后端就会把 home 翻译成：

    回到之前记住的 learning-commons

如果没有记录，后端会使用默认世界 vitality-gym-town。

所以 home 不是数据库里的一种真实位置。数据库真正保存的仍然是：

    vitality-gym-town
    learning-commons
    maker-harbor
    plaza

home 只是前端和后端之间约定的一个“召回动作”。

## 6. 第四步：数据库保存 location

位置：backend/app/models.py，第 18–30 行。

Agent 数据表中有一个字段：

    location

它表示 Agent 当前所在的位置。

后端把新的位置写进 Agent 对象，然后提交数据库事务。

SQLite 数据库文件的位置由 backend/app/db.py 第 5–10 行决定：

    backend/tamagotchi.db

因此这条链最后会落成一条数据库变化：

    某个 Agent 的 location
    从 learning-commons
    变成 plaza

这就是为什么刷新页面以后，位置仍然可以保留。

## 7. 第五步：后端把结果返回给手机端

后端保存完成后，会返回更新后的 Agent 信息，其中包括新的 location。

手机端收到结果后，会更新当前 Agent 详情中的位置，并通知外层页面刷新 Agent 数据。

相关位置仍然在 App.tsx 第 1668–1671 行附近。

另外，App.tsx 第 6648 行附近有 refreshMyAgents：

    重新向后端获取当前用户的 Agent 列表

所以页面最终可以根据最新的 location 判断：

    location 是 plaza
    → 在 Plaza 显示

    location 是三个世界之一
    → 在对应的世界显示

## 8. 把整条链压缩成一句话

    用户点击派遣
    → App 确定 Agent id 和目标位置
    → backendApi.dispatch 发送 POST 请求
    → backend/app/main.py 检查并修改 Agent.location
    → SQLite 保存位置
    → 后端返回更新结果
    → 手机端刷新列表和世界画面

这条链里，每一层都有自己的职责：

| 层                  | 负责什么                  |
| ------------------- | ------------------------- |
| 手机端界面          | 接收点击、显示结果        |
| backendApi.ts       | 把前端动作转换成后端请求  |
| backend/app/main.py | 检查规则、执行业务修改    |
| models.py           | 描述 Agent 有哪些数据字段 |
| db.py               | 连接 SQLite               |
| tamagotchi.db       | 保存真正的数据            |

## 9. 和顶部 Plaza 栏目的区别

现在可以比较两个容易混淆的动作。

### 点击顶部 Plaza

    改变手机端当前显示的栏目
    → App 选择显示 Public Plaza

主要是前端内部的显示状态。

### 点击派遣 Agent

    改变 Agent 的真实 location
    → 请求后端
    → 写入 SQLite
    → 影响 Scene 和 Plaza 的内容

这是跨越前端、后端和数据库的业务动作。

以后看到一个按钮，先判断它属于哪一种：

    只改变界面显示
    还是改变项目中的真实数据

## 10. 这条功能链对 AI 协作有什么用？

以后如果你要求 AI 修改“自动派遣 Agent”，你可以先让 AI 回答：

1. 前端从哪里触发自动派遣？
2. 是否仍然调用 dispatch 接口？
3. 后端需要增加什么规则？
4. location 和 home_world 是否仍然正确？
5. 页面和数据库怎样验证？

如果 AI 只修改了按钮文字，却没有处理后端和数据库，你就能发现它只改了表面。

如果 AI 修改了后端，却没有让手机端重新获取 Agent 列表，你就能预判页面可能显示旧数据。

这就是理解功能链的实际价值：你可以判断 AI 的修改是否覆盖了完整功能，而不需要亲自写出这套代码。

## 小结

- 派遣 Agent 会改变真实数据，不只是切换页面。
- 手机端负责接收点击并提交 Agent id 和目标位置。
- backendApi.dispatch 负责发出 POST 请求。
- backend/app/main.py 负责检查规则并修改 location。
- SQLite 保存新的 location，刷新后数据仍然存在。
- home 是召回动作，数据库保存的真实位置仍然是四个固定值之一。
- 读一个功能时，要沿着“用户动作 → 请求 → 后端处理 → 数据库 → 页面结果”追踪。
